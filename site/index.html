What's different

Built differently, and honest about the limits.

Most of what an agent harness does, every agent harness does. These are the parts that are different. Each one comes with its limit, written down.

Made for small context windows

Every decision is made with an 8k window in mind. A skill costs one line until it's needed. The plan sits at the end of the request, so prompt caching keeps working. Old tool results shrink before anything gets summarized. On a hosted model, that same care shows up as a smaller bill.

The limit: it won't make a small model smart. It makes running an agent on one affordable.

The context window →

One core, two frontends

The desktop app and the taurus CLI are the same agent, sharing ~/.taurus. A tool you approve in the app is approved for your scripts too. You can start a conversation in one and pick it up in the other.

The limit: they aren't identical. Diff review, commits and the terminal dock are only in the app.

How it's put together →

Undo covers what commands did

Taurus takes a snapshot of the workspace before each command and compares it afterwards. A sed -i across a dozen files, or an rm that hit the wrong folder, both come back. You don't need git for any of it.

The limit: it can't restore .git itself or ignored folders, and it tells you so before you rewind.

Rewinding a turn →

Uses the config you already have

Taurus reads AGENTS.md, CLAUDE.md, Copilot instructions, Claude and Copilot skills and sub-agents, Claude Desktop's mcpServers, and Claude Code plugins. It never writes to any of them.

The limit: it reads them but doesn't copy their behavior exactly. An applyTo glob, for instance, becomes a sentence in the prompt.

Instructions →

A new clone can't configure your agent

A repo's .taurus folder can start processes and decide where your conversation is sent. In a workspace you haven't trusted, it does nothing. When Taurus asks, it shows you the exact command lines, including any hidden characters.

The limit: trusting a repo isn't a sandbox. It doesn't control what that repo's build script does.

Trusting a workspace →

Data files open as tables

Give it a million-row CSV and it profiles every row and answers questions in SQL, refusing any query that does more than read. The rows show in their own pane and never fill the context window. Steps worth keeping become recipes you commit.

The limit: recipes are written in DataFusion's SQL dialect.

Permission

Every write is a diff first

Before anything touches disk, you see exactly what will change. You can approve it once, for this project, or everywhere. Hooks can refuse a call, but they can never approve one.

Permissions →
Undo

Rewind, fork, keep

  • Rewind any turn, including what its shell commands changed.
  • Fork a turn to try it another way or on another model, then switch back.
  • Keep a turn: read it back as a diff and commit it on its own.
  • Review a turn with an agent that hasn't seen the conversation.

The file, beside the conversation

Files open next to the chat, with the lines the model means already selected. Select a passage and click Ask about this. If Taurus changes a file while you're typing in it, both versions are kept and you choose.

Your shell, with a pass/fail mark per command

Press Ctrl+` for a real PTY at the bottom of the window. Ask Taurus turns a failed command and its output into a message. While the dock is open, the model can see your recent commands.

Quick start

Three ways to get started.

The first needs only the download. The second needs Rust. The third needs the full toolchain.

Each tagged release attaches installers for all three platforms to GitHub Releases. Once installed, the app updates itself from the same place.

macOS (Apple Silicon and Intel).dmg
Linux.AppImage, .deb, or .rpm
Windows.msi, or the -setup.exe installer
Latest release

You need Rust 1.89 or newer and a C compiler. You don't need Node, pnpm or the Tauri prerequisites, because dictation and reading aloud are desktop-only features. 

$ cargo install --path crates/taurus-cli

$ taurus repl                                     # interactive
$ taurus run "summarize the modules in src/"      # one-shot
$ taurus run --json "count the rust files" | jq   # for scripts
$ taurus rewind --to last                         # undo what the last turn wrote
$ taurus fork --at last                           # try it again, keeping the first try
$ taurus plugin add <folder or git URL>           # a Claude Code plugin, as it is
$ taurus memory add "staging has the migration"   # tell the next conversation something

You need Rust 1.89+, Node 22+, pnpm 12, the Tauri prerequisites, and CMake for the whisper.cpp speech engine. On Linux you also need libclang-dev and libasound2-dev. 

$ git clone https://github.com/Lukeus/taurus && cd taurus
$ pnpm install
$ pnpm tauri dev

If the build stops in whisper-rs-sys, see the speech engine.

A model to talk to

A local model is the quickest way to try it. Start Ollama and pull a model that can call tools. A first run needs no other configuration. 

$ ollama serve        # in another terminal
$ ollama pull qwen3:8b

Using a hosted model instead?

Anthropic, Gemini, OpenAI and anything OpenAI-compatible, including Azure and gateways. API keys are stored in your OS keychain or an environment variable, never in a config file.

Under the hood

Rust underneath. One rule on top.

A frontend contains no agent logic.

Config files, the system prompt, the tool registry and the skill library all live in taurus-host, and Host::build_agent is the only place a session is assembled. The app and the CLI differ only in how they ask you for permission. That's also why the agent loop can be tested against a scripted provider, with no GUI.

The provider types use Anthropic-style content blocks. No provider adapter after the first one needed a change to the core, and models without native tool calling still call tools through prompted parsing.
